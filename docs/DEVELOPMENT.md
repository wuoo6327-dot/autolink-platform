# 开发、验收和版本回滚

当前是第一轮隔离候选源码。源码变更、单元测试成功和扫描通过都不能写成已生产上线；生产、修复分支和待上线文件各自记录 commit / SHA256 与验收状态。

正式源码保存在私有 Git 仓库；main 保存经评审的版本，开发分支使用 `codex/<任务名>`。变更说明包含问题、范围、测试、数据库兼容和部署风险。先检查 git status，保护未提交内容，不在共享工作目录强制 reset 或切换多人分支。

`.env.example` 仅放空秘密字段和公开配置。production `.env`、数据库、私有上传、备份及原始扫描结果不进入 Git。CI 只读源码；生产权限属于独立且明确授权的运维流程。没有完整前端构建项目时，修改现有编译文件须限定范围、保留入口，不借修复重做界面和收费规则。

验收顺序：备份及隔离恢复演练 → 核对源码与秘密 / Git 边界 → 官方工具与源码 / 历史扫描 → 账号权限和上传安全 → 临时数据库业务闭环 → SEO / 九语言 / 性能 Gate。每阶段区分实际执行、未执行和未完成。合成测试数据明确标注，依赖升级要单独确认兼容性，不在 CI 自动 pip install -U。

给验收过的候选 commit 建立标记，例如 `autolink-2026-10-10-rc1`；生产部署并复查后再记录 release commit 和实际时间。候选标记不等于已经上线。

回滚方案要包含上一版本 commit / SHA256、旧容器或构建产物、数据库变更兼容性、可用备份与演练结果。保留稳定源码和构建产物，避免拼接未知历史目录。

应用回滚优先恢复稳定代码并保留业务数据；不要因代码回退就把旧 SQLite 覆盖到仍在变化的生产数据库。存在不兼容 schema 变更时，先在隔离恢复副本验证方案，再安排运维窗口。破坏性迁移必须配有独立恢复方案。

真正上线 / 回滚前要具备操作授权，并完成备份和兼容性验收。当前脚本和 CI 不执行部署、服务器修改或数据恢复。
